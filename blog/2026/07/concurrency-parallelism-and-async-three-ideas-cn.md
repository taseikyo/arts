## 一、为什么大家总把三者搞混？

根源在于三者都在回答同一个表层问题：**如何让程序同时处理多件事？** 但三者给出的底层解决方案天差地别。

用厨房厨师的例子直观区分：

1. **并发**：一名厨师独自做三道菜。先烧水煮意面，趁烧水间隙切蔬菜 —— 多任务交替推进，并非同时执行。

2. **并行**：餐厅多雇一名厨师，两人同步开工，一人做意面、一人拌沙拉 —— 多任务真正同一时刻运行。

3. **异步**：厨师给烤箱设好计时器，不用守在烤箱旁等待，转身去服务其他桌客人 —— 核心是等待时不阻塞自身流程。

同样一间厨房，三种完全不同的工作策略。

## 二、并发：多任务交替推进，而非同时执行

并发指多个任务**处于进行中**，但不一定**同一时刻执行**。
在单 CPU 核心环境下，处理器会在任务间高速切换，肉眼感知像是同步运行，但任意一个时钟周期，CPU 只会执行一条指令。

这套机制称为**时间片轮转**或**上下文切换**：操作系统给每个任务分配极小的执行时间片，到点就暂停任务、保存当前运行状态，切换到下一个任务。外部视角看仿佛多任务并行，底层只是高速轮流执行。

示意图特征：任意时刻，两个任务不会同步运行，只能交替执行。
总耗时不会缩短，但系统响应更流畅 —— 不会出现一个任务完全阻塞、其他任务排队等待的情况。

**并发最适合 IO 密集型任务**：读取文件、数据库查询、等待网络接口返回。这类场景中 CPU 会大量空闲等待，并发可以充分利用这段空闲时间处理其他任务。

## 三、并行：真正意义上的同步执行

并行指多个任务**在完全同一时间点**运行，每个任务独占一块 CPU 物理核心，不存在轮流执行。多核环境下，一个时钟周期就能同时执行多条指令。

这就是大家口中 “多线程提速” 的底层原理，但有两个关键前提：

1. 设备拥有**多块物理 CPU 核心**；

2. 任务之间无依赖关系（否则依旧需要互相等待）。

**并行擅长 CPU 密集型任务**：图像处理、视频编码、矩阵运算、机器学习推理。这类任务可拆分为多个独立子任务，多核同步运算能实现接近线性的性能提升。

### 并行的代价：共享状态冲突

并行会引入**共享内存竞争**问题：两个核心同时修改同一块内存数据时，运算结果不可预测，这就是**竞态条件（Race Condition）**。
想要规避该问题，必须引入互斥锁、信号量、原子操作等同步工具；但同步机制会增加代码复杂度，还可能引发**锁竞争**，反而拖慢整体性能。

这也是并行代码比并发代码更难写稳的原因 —— 多线程系统里很多故障隐蔽、复现概率低，难以定位。

## 四、异步 IO：等待过程不阻塞线程

异步是一种**编程模型**，而非硬件特性。它解决的核心问题：**单一线程如何高效处理大量任务，全程无空闲阻塞？**

核心机制是**事件循环**：执行数据库查询这类需要等待的操作时，异步程序不会阻塞当前线程，而是注册回调 / 后续执行逻辑，释放线程去处理其他任务；等 IO 结果返回后，再切回原任务继续执行。

案例：单线程同时发起两条数据库查询，两条请求几乎同时发出，总等待时长约等于两条查询中耗时更长的那一条（`max(用户查询耗时, 订单查询耗时)`），而非两者耗时相加，这是异步最核心的性能优势。

主流编程语言都为异步提供专用语法：JavaScript/Python/Rust 的 `async/await`、Ruby 纤程、Go 协程。运行时会把线性写法的代码转化为状态机，在`await`断点暂停、恢复任务。

### Ruby 纤程模拟异步示例

```ruby
require 'fiber'
# 模拟查询用户
fetch_user = Fiber.new do
  puts "正在拉取用户数据..."
  sleep(1) # 模拟数据库等待耗时
  Fiber.yield "用户：Alice"
end
# 模拟查询订单
fetch_orders = Fiber.new do
  puts "正在拉取订单数据..."
  sleep(1) # 模拟数据库等待耗时
  Fiber.yield "订单：[#1, #2, #3]"
end

# 两个纤程协作调度，互不阻塞
user   = fetch_user.resume
orders = fetch_orders.resume
puts user
puts orders
```

生产环境的 Ruby on Rails 项目，可通过 Async 组件或 Falcon Web 服务器实现纤程异步 IO；单个 Rails 进程无需创建数千条线程，就能承载大量并发请求。

## 五、三者的关联关系

三者并非互斥，线上真实系统往往会同时结合三种方案。

> 核心总结：
> **并发描述程序架构**（如何设计程序以处理多任务）；
> **并行描述执行方式**（任务是否在硬件层面同步运行）；
> **异步是一种轻量化实现并发的技术**，无需多线程即可达成并发效果。
> 
> 

Go 语言联合创始人 Rob Pike 有一句经典概括：
**并发是同时处理一堆事，并行是同时做一堆事。**

## 六、选型决策框架

遇到性能、扩容问题时，按以下 4 个问题依次判断方案：

1. **瓶颈是 CPU 还是 IO？**
务必先做性能采样分析。绝大多数 Web 应用属于 IO 密集型：数据库、缓存、第三方接口耗时占总响应时间 80%\~95%。给 IO 密集型业务增加并行逻辑，通常无法提升性能。

2. **同时运行的任务量级有多少？**
几十条线程完全可控；上千条线程成本极高 ——Ruby、Java 每条线程栈内存占用约 1\~8MB。若需要承载上万并发连接，异步的内存利用率远高于多线程。

3. **任务之间是否共享数据状态？**
存在共享状态时，所有方案复杂度都会上升。单事件循环的异步天然规避共享竞争；并行方案则需要额外加锁，或使用不可变数据结构。

4. **当前运行时原生支持哪种方案？**

- Ruby 的全局虚拟机锁（GVL）无法让普通线程实现真正并行；Ruby3\.0 推出的 Ractor 支持隔离式并行。

- Node\.js 原生单线程 \+ 异步 IO 架构。

- Go 从底层设计就适配协程并发，轻量执行单元成本极低。

## 七、Ruby 语言的优势与短板

Ruby 的迭代历程能直观体现行业对并发 / 并行 / 异步的理解演变。
经典 MRI Ruby 存在**全局虚拟机锁（GVL/GIL）**：即便多核机器，同一时间也只有一条 Ruby 线程执行代码。该机制杜绝了大部分竞态问题，但普通线程仅能实现并发，无法并行。

对绝大多数 Rails IO 密集型业务而言，该限制无伤大雅：程序等待 IO 时会释放 GVL，数据库查询、HTTP 请求阶段多线程可并发调度。

Ruby3\.x 推出**Ractor**，基于 Actor 模型实现真正并行：每个 Ractor 拥有独立堆内存，通过消息传递通信，完全消除共享状态；代价是跨 Ractor 传输对象有严格限制。

### Ruby3 Ractor 并行代码示例

```ruby
# 两个Ractor分别在独立操作系统线程运行，真正并行计算
ractor1 = Ractor.new { (1..10_000).reduce(:+) }
ractor2 = Ractor.new { (10_001..20_000).reduce(:+) }
result = ractor1.take + ractor2.take
puts result  # 输出 200010000
```

与此同时，`async`库为 Ruby 提供协作式并发（事件循环模式），写出的异步代码逻辑贴近同步写法，Rails 开发者极易上手。

## 八、阿姆达尔定律（Amdahl's Law）

在盲目并行化之前，有一条无法规避的性能上限定律：
若程序中仅有比例`p`的代码可并行化，使用`N`颗处理器时，理论最大加速比`S`计算公式：

举例：若 50% 代码只能串行执行，无论增加多少核心，最大加速比仅为 2 倍，无法做到 10 倍、百倍提速。

这也是优化前必须做性能采样的原因：若程序 90% 耗时卡在串行瓶颈，再多 CPU 核心也无法显著提升性能。

## 九、常见认知误区纠正

### 误区 1：多线程一定能提速

仅在同时满足以下条件时成立：任务为 CPU 密集型、子任务完全独立、存在闲置 CPU 核心。
IO 密集型业务使用成熟异步服务器时，多线程只会增加额外开销，无性能收益。

### 误区 2：异步等同于并行

错误。Node\.js、Ruby 异步服务均为单线程架构，多个请求只是交替并发处理，绝不会同步执行。针对 CPU 密集型运算，异步没有任何优势。

### 误区 3：并发开发风险高

取决于实现方式：单事件循环异步方案几乎无并发风险；带共享状态的多线程才是故障高发区。Actor 模型（Ractor、Erlang 进程）彻底摒弃共享内存，大幅降低并发系统开发难度。

### 误区 4：GVL 让 Ruby 线程毫无用处

对绝大多数 Rails IO 密集型业务，线程实用性很强：等待数据库、HTTP 接口时 GVL 会释放，线程可并发调度；GVL 仅会限制 CPU 密集型运算性能。

## 十、整体分层总结

三者可以形成一套分层思维模型：

1. **异步**：单线程最大化 IO 效率的编程手段；

2. **并发**：更宽泛的程序设计思路，通过异步或时间片线程实现多任务推进；

3. **并行**：依托多核硬件，拆分 CPU 密集任务同步运算，获得算力提升。

线上系统通常三者结合使用：
Web 服务器通过异步 IO 承载上万并发连接；无法异步改造的阻塞操作启用线程池；图片压缩、PDF 生成等重度 CPU 任务，交给后台工作池分发到多核并行运算。

分清三者的适用场景与底层原理，才能搭建出平稳扩容的系统，避免高负载下服务崩溃。
