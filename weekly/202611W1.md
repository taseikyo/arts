### 1. [为什么很多80后、90后都很不成熟，不能独当一面，甚至还需要父母为其遮风挡雨?（知乎）](https://www.zhihu.com/question/2010917375269168970)

> 来自 [道一](https://www.zhihu.com/people/dao-yi-48) 的 [回答](https://www.zhihu.com/question/2010917375269168970/answer/2047657675488602052)，发布于 2026-06-09 12:33

我一直认为，80.90后，尤其是83-97这十五年左右的人，是中国历史上，前无古人后无来者的，一代人格高度健康、而科学的，代际人群。

（关于这个代际，有兴趣的朋友也可以，跳到我这个回答看一下。主要说：

为什么85-95这代人，是中国有史以来，从原始人以来，在“婚恋问题”上，被原生家庭折磨的最惨、最痛苦的一代人”）

因为这十五年左右之内的人，保留了中国传统社会形态里的优点，又吸收了现代化社会的优点。

83以前的人，还有强烈的，传统社会里的很多劣根性；

97以后的人，已经彻底把，一切传统抛弃了，无论好坏。

83以前的人，盛产“以自我牺牲为爱好，同时精神绑架亲密关系”的PUA患者，所谓老登。

核心人格面貌是：我为你，吃苦吃死，让你对我俯首帖耳、卑躬屈膝，过分吗？

97以后的人，盛产“以精致利己为爱好，同时彻底抛弃亲密关系”的自私症患者，所谓魔丸。

核心人格面貌是：你死不死，和我有什么关系？反正谁敢让我不爽，就给我死！

只有83-97这十五年左右出生的人，群体性地做到了，付出和索取、利己和利他的平衡。

只有这代人，大部分都能做到，追求自己的自由的同时，不妨碍别人；

索取自己的利益的同时，也愿意为别人尽可能着想。

因此，这代人，是最早一批，成代际地站出来明说，“不求孩子什么，先愿自己的孩子健康、快乐地成长”；（想想他们的父母们，怎么对待他们的学习和成长）

同时，这代人，也是最后一批，成代际地站出来明说，“我愿意为我爱的异性，为家庭、配偶，吃苦付出、同甘共苦”。（想想97以后的人，越来越怎么对待爱情、对待婚姻，想想05后的人，怎么越来越把谈恋爱的人，女的当成“媚男”，男的当成“舔狗”）

所以大到做生意、交朋友，小到排队、买东西、陌生人闲聊，我都尽可能，只和大概这个代际的人接触。

事实也证明，最有礼貌、最有教养、最友善真诚的人，差不多也都是，这个代际的。

而老的和小的，各有各的，给人折磨之处。

补更一下，我回复评论区总结的，一些我认为97以后年轻人，精神面貌和教养素质下滑的，素材依据：

明显的下滑，确实是从94前后开始的，但是直到97左右还能多少保持住，一点之前的精神面貌。

我之所以定97，是因为97.98以后，那个下滑已经不能用明显来形容，而是断崖式地跌落。

评论区里，有一个家里在中学门口，开了多年小吃部的朋友，也是说类似的话。

他说他们一家人，眼睁睁地看着，中学生的精神面貌和教养素质，从90后的样子，跌落到现在10后的程度。

我前两天回母校怀旧了一下，母校门口面馆的老板，聊天我说我毕业十来年了，他也是这样说：

“现在这孩子们不知道怎么了。

你们那时候大学生，都是呼朋唤友，见面也爱和我打招呼、聊聊天，叫个大哥什么的。

### 2. [10道系统设计题，这次全是场景设计和开放题，值得收藏](https://mp.weixin.qq.com/s/j6xancgTOjoclNk3jOpQXQ?scene=1)

> 小小面试凶巴巴 java面试题目必背 2026年10月19日 14:05 上海

#### 1. 设计一个秒杀系统

及格线：

前端限流（按钮置灰、验证码）、后端限流（令牌桶）、Redis 缓存库存、MQ 削峰。

加分项：

说清楚完整流程——提前把商品库存加载到 Redis（库存预热）；用户点击秒杀时先校验资格（黑白名单、频率限制），再扣减 Redis 库存（lua 脚本保证原子性）；扣减成功后发送 MQ 消息，异步落单和扣减数据库库存。再补充关键点：数据库库存用乐观锁（CAS）或悲观锁（for update）；订单表做分库分表；静态资源 CDN 加速；秒杀页面静态化。如果能提到防作弊（同一用户限购、设备指纹识别），会显得考虑周全。

> 翻车点：有人说 “用数据库行锁保证库存不超卖”——行锁在高并发下性能很差，应该先用 Redis 做前置过滤。

#### 2. 设计一个短链接系统

及格线：

用哈希算法（MD5、CRC32）将长链接转成短码，存入数据库，访问时 302 重定向到长链接。

加分项：

说清楚几个关键设计——短码生成：用发号器（雪花算法或数据库自增 ID）转 62 进制（0-9a-zA-Z），比哈希更可控，不会碰撞。存储：用 Redis 做缓存（key 为短码，value 为长链接），MySQL 做持久化。重定向用 301 还是 302：301 是永久重定向，浏览器会缓存，减少服务器压力但无法统计点击量；302 是临时重定向，可以统计点击次数。再补充：短链接的过期策略、防攻击（恶意生成大量短链接）、自定义短链接功能。

> 面试官常追问：如果发号器挂了怎么办？答：可以做双机房部署或用 Snowflake 替代。

#### 3. 设计一个 IM 即时通讯系统

及格线：

客户端和服务端通过 WebSocket 保持长连接，消息经服务端转发。

加分项：

说清楚架构分层——接入层（WebSocket 网关集群，负责维持连接和心跳）；逻辑层（消息路由、会话管理、离线存储）；存储层（消息存 MySQL 或 Cassandra，离线消息存 Redis）。再补充关键设计：消息 ID 用全局唯一 ID（雪花算法）；消息可靠性（客户端 ACK 确认，超时重传）；消息顺序性（同一个会话的消息用同一个队列处理）；多端同步（记录 lastMessageId，拉取增量消息）。如果能提到万人群聊的优化（消息扩散写 vs 扩散读），会非常有深度。

> 面试官常追问：怎么保证消息不丢不重？答：不丢靠 ACK + 重传，不重靠客户端去重（用消息 ID）。

#### 4. 设计一个支付系统

及格线：

订单创建→调用支付网关→支付回调→更新订单状态。

加分项：

说清楚几个关键设计——幂等：支付回调用订单号 + 支付流水号做去重；状态机：订单状态（待支付→支付中→支付成功 / 支付失败 / 退款中 / 已退款）用状态模式管理，不允许跳跃变更；对账：每天和支付渠道对账，差异部分人工处理或自动补偿；资金安全：所有金额用分存储（整数），避免浮点数精度问题。再补充：退款走异步流程，审核通过后调用支付渠道退款接口，失败后定时重试。

> 翻车点：有人说 “支付成功直接更新订单状态”——应该先校验签名、验重、记录流水，再更新订单状态。

#### 5. 设计一个评论系统

及格线：

评论表包含帖子 ID、用户 ID、内容、时间，按帖子 ID 查询。

加分项：

说清楚几个难点——评论排序：按时间倒序（最新评论在前）或按热度排序（点赞数 + 回复数加权）；评论分页：用游标分页（cursor based）代替 offset 分页，避免深度分页性能问题；评论计数：用 Redis 缓存每个帖子的评论数，异步同步到数据库。再补充：楼中楼设计（两级评论还是无限层级？一般两级就够了，无限层级对产品价值不大但复杂度飙升）；敏感词过滤（用 DFA 算法或第三方接口）；删除评论的处理（逻辑删除，保留子评论）。

> 面试官常追问：热评怎么计算的？答：可以按点赞数 + 回复数 + 时间衰减因子综合评分，定时任务重新计算。

#### 6. 设计一个 Feed 流系统

及格线：

用户发动态后，粉丝刷新时看到最新的动态列表。

加分项：

说清楚两种主流方案——推模式（写扩散）：用户发动态后，写入所有粉丝的收件箱（Feed 表），读时直接查收件箱。适合粉丝少的场景。拉模式（读扩散）：用户发动态后只写入自己的发件箱，粉丝刷新时拉取所有关注者的动态再合并排序。适合大 V 场景。实际中常用推拉结合：普通用户用推模式，大 V 用拉模式（粉丝上线时拉取）。再补充 Feed 的排序：按时间倒序或按热度排序；Feed 的缓存：收件箱用 Redis 的 List 或 SortedSet 存储。

> 面试官常追问：推模式下粉丝很多怎么办？答：异步批量写入，或者只推送给在线用户，离线用户上线时拉取。

#### 7. 设计一个打车系统

及格线：

乘客发单→系统匹配附近司机→司机接单→行程开始→行程结束→支付。

加分项：

说清楚几个关键设计——司机定位上报：每隔几秒上报经纬度到 Redis GEO（地理位置数据结构）；乘客发单后，用 Redis GEO 搜索附近司机（半径 3 公里内）；派单策略：距离最近优先、评分最高优先、或抢单模式。再补充：订单状态的分布式事务（乘客发单、司机接单、行程开始、行程结束，每个状态变更都要保证一致性）；价格计算（起步价 + 里程费 + 时长费 + 动态调价）；防刷单（轨迹偏差检测、异常订单识别）。

> 面试官常追问：高峰期怎么动态调价？答：根据供需比（附近订单数 / 附近空车数）动态调整倍率，引导供需平衡。

#### 8. 设计一个日志采集系统

及格线：

应用打印日志到文件，Filebeat 采集，送到 Logstash 处理，最后存到 Elasticsearch，Kibana 展示。

加分项：

说清楚完整链路和优化点——日志采集端：用 Logback 的异步 Appender 避免日志影响业务性能，日志格式统一（JSON 格式便于解析），加 traceId 做链路追踪。传输层：用 Kafka 做缓冲，应对日志峰值流量，Logstash 从 Kafka 消费。存储层：ES 按天建索引，冷热数据分离（热节点 SSD，冷节点机械硬盘），设置索引生命周期管理（ILM），定期删除过期索引。再补充：日志级别动态调整（通过配置中心实时修改线上日志级别，排查问题时临时开 DEBUG）。

> 翻车点：有人说 “日志直接打到 ES”——高峰时期 ES 扛不住，中间必须加消息队列缓冲。

#### 9. 设计一个配置中心

及格线：

配置存储在服务端，客户端启动时拉取配置，支持配置变更后动态刷新。

加分项：

说清楚几个关键设计——配置存储：用数据库持久化，Redis 做缓存加速读取；客户端拉取：启动时全量拉取，运行中通过长轮询（long polling）监听配置变更，变更后增量推送；配置隔离：按环境（dev/test/prod）、按应用、按集群隔离；配置版本管理：每次修改生成新版本，支持回滚；配置热加载：Java 中通过 EnvironmentChangedEvent 或 @RefreshScope 实现 Bean 属性的动态刷新。如果能提到 Apollo 或 Nacos 的设计思路（命名空间、集群、配置项的三级划分），会非常加分。

> 面试官常追问：长轮询和 WebSocket 有什么区别？答：长轮询是客户端发起请求，服务端 hold 住直到有变更或超时返回；WebSocket 是双向通信，服务端可以主动推送。

#### 10. 设计一个短消息（短信）发送系统

及格线：

业务系统调用短信接口，短信服务调用第三方短信通道发送，记录发送结果。

加分项：

说清楚几个关键设计——通道管理：对接多个短信通道（阿里云、腾讯云、AWS SNS），做负载均衡和故障切换；发送策略：重要短信（验证码）走高优先级通道，营销短信走低价通道；限流：每个手机号每分钟最多发几条，每天最多发几条，防止被刷；重试机制：发送失败后按指数退避重试（1 分钟、5 分钟、15 分钟、1 小时），超过最大重试次数后人工介入。再补充：短信内容的模板化管理（避免拼接 SQL 注入和内容合规问题），发送记录的统计分析（成功率、到达率、响应时间）。

> 面试官常追问：怎么保证短信不重复发送？答：业务方传唯一 ID，短信服务端做幂等，同一个 ID 只发一次。
