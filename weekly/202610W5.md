### 1. 一个研发领域的“六边形战士”

> 这个是我问 chatgpt 的一个问题，人们常用“六边形战士”来形容一个人很全面，比如乒乓球领域的马龙；因此我问 chatgpt，作为一个研发，他的六个角的能力应该是什么？

如果让我定义一个研发领域的“六边形战士”，我不会单纯看他掌握了多少技术、会多少编程语言，而是看他能否理解问题、设计方案、交付结果，并且让团队持续创造价值。

#### 1. 问题理解与业务抽象

核心问题：做什么，为什么做？

能否从模糊的业务需求中识别真正的问题，理解业务目标、用户需求和约束条件，并将其转化为清晰的技术问题。

- 不只是接收需求，而是能够质疑不合理的需求。
- 不只是理解功能，而是理解功能背后的业务价值。
- 能够区分“用户提出的解决方案”和“用户真正想解决的问题”。

高阶表现： 需求还不清晰时，就能帮助团队把问题定义清楚。

#### 2. 技术深度与工程能力

核心问题：能不能把东西做好？

这是研发的基本盘，涵盖编程、数据结构、数据库、网络、并发、分布式系统、性能优化、故障排查和代码质量。

- 能写出正确、清晰、可维护的代码。
- 理解底层原理，而不只是会调用框架。
- 面对线上故障，能够定位根因，而非仅靠重启解决。
- 能够平衡性能、可靠性、可维护性与开发成本。

高阶表现： 遇到复杂问题时，能深入底层定位并解决，而不是依赖不断堆叠工具。

#### 3. 系统设计与架构决策

核心问题：应该怎么做？

能否把多个技术组件组织成可靠、可扩展的系统，并在复杂约束下做出合理的技术取舍。

- 能够进行模块划分、数据建模和接口设计。
- 理解容量、延迟、一致性、可用性与成本之间的权衡。
- 能识别技术方案的边界条件和潜在故障模式。
- 知道什么时候应该引入复杂架构，什么时候简单实现更合适。

高阶表现： 不追求最先进的架构，而是能找到最适合当前业务阶段的架构。

#### 4. 交付能力与结果意识

核心问题：能不能把事情做成？

研发不是写完代码就结束，而是要对最终交付的结果负责。

- 能拆解任务、识别依赖、评估风险并安排优先级。
- 能在时间、资源和质量约束下完成目标。
- 能推动联调、测试、上线、监控和问题闭环。
- 能根据反馈调整方案，而不是执着于最初的技术设计。

高阶表现： 在目标不清晰、资源不足、依赖复杂的情况下，依然能够持续推动事情向前。

#### 5. 沟通协作与影响力

核心问题：能不能让别人和自己一起把事情做好？

软件研发通常不是单人作战。能力越往上走，越需要通过沟通和协作放大个人价值。

- 能向产品解释技术限制，向管理者说明风险和收益。
- 能推动跨团队协作，解决接口、排期和责任边界问题。
- 能进行有效的 Code Review、技术讨论和知识传递。
- 能指导其他开发者，帮助团队形成共识。

高阶表现： 不依赖职级和行政权力，也能通过专业判断与信任推动团队达成目标。

#### 6. 学习进化与不确定性应对

核心问题：面对未知，还能不能持续解决问题？

技术在不断变化，业务也在变化。比掌握多少现有知识更重要的，是面对新问题时的学习和适应能力。

- 能快速理解陌生技术、业务领域和代码库。
- 能通过实验、数据和文档验证假设。
- 能从故障、失败和错误决策中总结规律。
- 能在信息不完整的情况下做出暂时合理的决策，并及时修正。

高阶表现： 不需要等别人给出完整的方法论，也能逐步找到可行路径。

#### 为什么是这六种，而不是其他能力？

我会把它们分成三个层次：

判断层

① 问题理解 + ③ 系统设计

决定方向是否正确。问题理解错了，代码写得再好也可能是在浪费资源；架构判断错了，执行效率越高，后续返工可能越大。

执行层

② 技术深度 + ④ 交付能力

决定方案能否真正落地。一个人可以有很好的想法，但如果没有技术实现能力和结果意识，就很难创造实际价值。

放大层

⑤ 沟通协作 + ⑥ 学习进化

决定个人价值能否持续放大。前者让能力影响更多人，后者让能力适应新的问题和环境。

这六种能力有一个共同点：它们不只是适用于某个技术栈，而是能够伴随研发从初级工程师成长到资深工程师、技术负责人，甚至 CTO。

#### 如果要真正评估一个研发，怎么打分？

我建议每项采用 1～5 分，而不是简单地用“会/不会”来判断。

| 分数  | 能力表现                |
| --- | ------------------- |
| 1 分 | 需要明确指导才能完成          |
| 2 分 | 能独立完成常规任务           |
| 3 分 | 能独立解决复杂问题           |
| 4 分 | 能处理模糊问题，并指导他人       |
| 5 分 | 能建立方法、机制或体系，让整个团队受益 |

需要注意：评分应当基于实际案例，而不是自我评价。比如，评价系统设计能力时，不只问“你懂不懂微服务”，还要问他曾经做过什么决策、为什么这么选、出现过什么问题，以及最终结果如何。

#### 不同阶段，六边形的形状也应该不同

初级研发：把事情做对

重点是技术深度、问题理解和基本交付能力。首先能够可靠地完成任务，逐渐形成独立解决问题的能力。

高级研发：把复杂事情做好

重点转向系统设计、复杂问题解决、交付和技术判断。不再只是完成别人分配的任务，而是能负责一个完整的技术领域。

技术骨干 / 技术负责人：让团队把事情做好

六项能力都重要，尤其需要加强业务理解、架构决策、交付推进和团队影响力。个人编码能力仍然重要，但不再是衡量价值的唯一标准。

#### 我的最终判断

如果只能用一句话概括，我会这样定义一个优秀的研发：

**能理解正确的问题，做出合理的技术决策，扎实地解决问题，持续交付结果，并通过协作和学习不断放大自己的价值。**

另外，我认为还有一个值得单独讨论的问题：这六种能力中，哪一种最能区分普通研发和真正优秀的研发？

我的倾向是：初中级阶段，差距往往体现在技术深度；到了高级研发阶段，差距更多体现在问题抽象、技术判断和交付能力；到了技术负责人阶段，差距则体现在能否让团队整体变得更强。

也就是说，真正的“六边形战士”不一定每一项都达到满分，而是没有明显的致命短板，并且能够根据所处阶段，把最关键的能力发挥出来。

### 2. 研发人员最值得培养的六种软实力

#### 一、六种软实力

1. 沟通表达：让复杂的事情变得容易理解

不只是表达清楚，而是能根据听众的背景，决定应该讲什么、讲多深、先讲什么。

核心能力：结构化表达、倾听、提问、根据对象调整表达方式。

2. 协作推进：让一群人有效地完成一件事

不仅完成自己的任务，还能明确责任、协调依赖、提前暴露风险，减少团队中的等待和返工。

核心能力：目标对齐、任务拆解、依赖管理、风险沟通。

3. 影响力：让好的想法真正落地

技术方案正确，并不代表别人就会接受。你需要理解不同人的关注点，说明收益和代价，并推动形成共识。

核心能力：说服、协商、建立信任、处理分歧。

4. 判断与决策：在信息不完整时做出合理选择

现实中的研发工作，很少有所有条件都确定的情况。你需要判断什么值得做、什么可以延后、什么风险可以接受。

核心能力：权衡取舍、识别关键变量、评估风险、及时调整。

5. 培养他人：让团队不再依赖你一个人

从自己解决问题，进阶到帮助其他人独立解决问题。既要能够指导，也要懂得授权，而不是事事亲自接管。

核心能力：反馈、辅导、知识传递、合理授权。

6. 自我认知与情绪管理：在压力下依然有效地工作

识别自己的情绪、偏见和行为模式，在冲突中保持判断力，也能够接受反对意见和修正自己的观点。

核心能力：自我觉察、情绪调节、接受反馈、复盘。

这六项能力彼此关联，但不需要同时提升。

#### 二、最重要的不是学会说话，而是改变你处理问题的方式

很多人提升软实力时，会先想到看沟通类书籍、学习表达技巧、练习演讲。

这些当然有帮助，但我更建议你从工作中反复出现的真实场景入手。

下面用三个研发工作中的例子说明。

##### 场景 1：你认为某个技术方案不合理

假设另一个开发提出了一套方案，而你认为它会带来严重的扩展性问题。

比较低效的表达是：

> 这个方案不太好，后续会有很多问题，我建议重新设计。

即使你的判断正确，这种表达也可能让对方感到自己的工作被否定，同时也没有提供足够的信息来支持你的结论。

更好的方式是：

1. 先明确目标： 我们希望这个方案解决什么问题？
2. 解释判断依据： 当前方案在哪些负载、故障或扩展场景下存在风险？
3. 呈现权衡： 现有方案的优势是什么，代价又是什么？
4. 提出选择： 我建议采用哪个方案，以及为什么。
5. 邀请补充： 是否存在我尚未考虑到的约束？

这背后其实是一种很重要的能力：把“我认为你错了”，转变为“我们如何共同找到更好的方案”。

你不需要放弃自己的判断，而是要让判断更容易被理解、检验和接受。

##### 场景 2：项目推进不顺利，其他团队一直没有给出结果

这时，单纯催促往往效果不好。

例如：

> 这个接口什么时候能完成？我们这边一直在等。

这句话传递了压力，但不一定能解决问题。

可以换一种方式：

> 我们这边预计周四开始联调，目前还依赖你们的接口。如果接口周三无法交付，整体测试可能会顺延。现在主要卡在哪个环节？我们可以一起看看是否有临时方案，先保证核心流程能够跑通。

这段话同时做了四件事：

- 说明共同目标。
- 明确依赖和影响。
- 了解对方的真实困难。
- 提供解决问题的可能性。

协作推进的本质，不是让别人按你的要求做事，而是让各方能够围绕共同目标采取行动。

当然，如果问题涉及明确的责任、交付承诺或重复违约，也需要及时升级风险，而不是无限度地替别人兜底。

##### 场景 3：你发现同事的代码质量不好，想帮助他提高

技术骨干容易遇到一个陷阱：看到问题后，直接自己修改代码，或者一次性指出所有缺陷。

短期来看，这样最快；长期来看，团队可能会越来越依赖你。

更有效的方法是区分三种情况：

- 能力不足： 解释原理，提供示例，一起完成一次。
- 经验不足： 分享判断方法，让对方尝试独立解决。
- 责任心或执行问题： 明确预期、交付标准和反馈机制，而不是一味辅导。

你可以先问：

> 你当时为什么选择这种实现方式？你认为这里最大的风险是什么？

这个问题可以帮助你判断，对方究竟是不知道、不理解，还是没有认真考虑。

这也是培养他人的关键：不只是告诉别人正确答案，还要帮助别人形成独立判断的能力。

#### 三、如果每天只有 15～20 分钟，如何练习软实力？

我推荐一种方式：把软实力训练嵌入你本来就要做的工作中。

1. 每天：刻意练习一个微动作

例如，开会前先写下自己的结论和依据；讨论分歧时，先复述对方的观点，确认自己理解正确；推进项目时，明确下一步的责任人和时间点。

耗时：额外约 5 分钟，主要发生在原有工作中。

2. 每周：复盘一次真实互动

选择一场会议、一次技术争论或一次跨团队协作，思考：我的目标是什么？对方真正关心什么？我在哪个环节可以做得更好？

耗时：10～15 分钟。

3. 每月：选择一项能力进行针对性改进

比如这个月专注于结构化表达，下个月专注于跨团队推进。观察真实结果，并向可信任的同事征求具体反馈。

耗时：不需要额外安排固定课程，重点在实践与反馈。

你甚至可以在每周复盘时，只回答三个问题：

- 这周哪次沟通最有效？为什么？
- 哪次沟通出现了误解、阻力或不必要的返工？
- 下周我准备尝试改变哪个具体行为？

这样的学习方式还有一个好处：你不需要在疲惫的晚上继续啃一本沟通学书籍，也能持续积累。

#### 四、如果想系统学习，我会推荐哪些书？

如果你确实希望通过阅读建立体系，我建议从少量经典书籍开始，而不是一次性收集大量课程。

- 《关键对话》

适合：沟通与冲突处理

学习如何在意见不一致、情绪升高、利益冲突时，依然能够进行有效讨论。对于技术方案争论、需求变更和跨团队协作尤其有参考价值。

- 《谈判力》

适合：协商与影响力

帮助你区分立场与利益，寻找各方都能接受的解决方案，而不是把讨论变成谁说服谁。

- 《The Manager's Path》

适合：技术骨干向技术领导者发展

涉及技术领导、指导他人、团队协作和管理职责。即使你暂时不打算成为正式管理者，也可以从中理解技术领导力的工作方式。

我的建议是一次只读一本，并且每次阅读都对应一个真实问题。例如，最近正在经历跨团队协作困难，就优先学习协商与沟通，而不是机械地按照书单全部读完。

#### 五、怎样判断自己的软实力真的提高了？

我认为最重要的一点是：不要用“我现在说话是不是更流畅”作为主要标准。

软实力最终应该体现在工作结果和协作质量上。

你可以观察以下变化：

| 能力   | 可以观察到的进步              |
| ---- | --------------------- |
| 沟通表达 | 别人更快理解你的观点，反复解释和误解减少  |
| 协作推进 | 任务责任更明确，依赖问题更早暴露      |
| 影响力  | 不依赖职位权力，也能推动合理方案落地    |
| 判断决策 | 能解释为什么这样选，也能识别自己的判断边界 |
| 培养他人 | 团队成员能够独立解决更多问题        |
| 自我认知 | 遇到分歧时，更容易区分事实、推测与情绪   |

这些变化不一定每次都能精确量化，但可以通过项目复盘、同事反馈和实际协作结果逐渐观察出来。
